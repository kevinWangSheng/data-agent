# IM 入口取证：Slack / Telegram / Discord（2026-11-23）

只取证，不做设计决定。nao、dash、SignalPilot 的路径都在 `~/dev/AI/data-agent-refs/` 下（下文省略前缀）。网页访问日期均为 2026-11-23。本仓库 HEAD `a6e918b`。

## 结论摘要（只列事实）

1. nao 用一个第三方库 `chat`（含 `@chat-adapter/slack|telegram|teams|whatsapp`）做统一收发；`Provider` 类型含 slack、teams、telegram、mattermost、whatsapp、automation，没有 Discord（`apps/backend/src/types/messaging-provider.ts:46`）。`messaging-provider.ts` 只是类型文件，不是接口抽象；每个平台是一个独立的 service 类，流程基本复制粘贴。
2. nao 的 Slack 支持 webhook 与 Socket Mode 两种收消息方式，Telegram 只有 webhook（`telegram.ts:77` `mode: 'webhook'`）。
3. nao 一个 IM 线程对应一条 chat：`chat` 表有 `slack_thread_id`、`telegram_thread_id` 等列（`db/sqlite-schema.ts:343-347`），按线程 id 查，查不到就建。
4. nao 的澄清提问在 IM 里是纯文本编号列表（`utils/messaging-provider.ts:456-462`），没有按钮；用户直接回文字。
5. nao 流式更新靠反复编辑同一条消息（节流 200ms，`telegram.ts:36`），不是一次性回复。
6. nao 的 Telegram 绑定表是进程内存里的 Map（`telegram.ts:45`），重启后丢失；Slack 靠 Slack 邮箱匹配 nao 用户。
7. nao 里与这些消息文件相关的文件，逐个 grep 都没有 `@license Enterprise`（见题 1 的检查记录）。
8. 本仓库对话 API 无鉴权，只绑 `127.0.0.1`（`src/data_agent/cli.py:35,481`）。新建对话、发消息或插话、取消、读事件都有 HTTP 接口；澄清回答就是一条普通消息。IM 适配器可作为本机 HTTP 客户端调用。
9. 三个平台都能不开公网地址收消息：Slack Socket Mode、Telegram `getUpdates`、Discord gateway。Python 库许可证：slack_bolt MIT、aiogram MIT、discord.py MIT、python-telegram-bot LGPL-3.0。

## 题 3：不开公网地址的官方方式

### Slack Socket Mode

- 来源：<https://docs.slack.dev/apis/events-api/using-socket-mode/>（2026-11-23）。
  - 用 app-level token 调 `apps.connections.open` 取 WebSocket URL，token 放 `Authorization` 头；URL 会定期刷新，需要快速重连。
  - 每个事件都要用 `envelope_id` 确认，否则 Slack 会重试；WebSocket 已预认证，不需要校验签名。
  - 最多同时 10 个 WebSocket 连接。
  - "Apps using Socket Mode are not currently allowed in the public Slack Marketplace"；可用于组织内部分发。
  - 仅限使用细粒度权限的应用（2019-12 之后创建的都是）。
- app-level token 的 scope 是 `connections:write`：<https://docs.slack.dev/reference/scopes/connections.write>（2026-11-23）。
- bot scopes 具体清单：未查官方页，dash 的 manifest 可作参照（见 2.1），属第三方示例。
- 许可证（`api.github.com` 与 LICENSE 原文，2026-11-23）：`slackapi/bolt-python` MIT（最近推送 2026-11-18）；`slackapi/python-slack-sdk` MIT。

### Telegram `getUpdates`

- 来源：<https://core.telegram.org/bots/api>（2026-11-23）。
  - 长轮询，`timeout` 参数单位秒，默认 0 即普通短轮询（仅供测试）。
  - 收更新只能二选一：getUpdates 或 webhook，"two mutually exclusive ways"；设了 webhook 时 getUpdates 不可用。
  - `limit` 1-100，未取走的更新最多保留 24 小时。
- 库许可证：
  - `aiogram/aiogram`：MIT（LICENSE 原文，最近推送 2026-11-23）。
  - `python-telegram-bot`：`pyproject.toml` 写 `LGPL-3.0-only`，`LICENSE.lesser` 存在；仓库 `LICENSE` 文件是 GPL-3 文本，GitHub API 探测结果显示 GPL-3.0，README 写 LGPLv3。三处不一致，以 pyproject 和 README 为准是 LGPL-3.0，但需要在使用前再核对。

### Discord gateway

- 来源：<https://docs.discord.com/developers/topics/gateway>（2026-11-23；旧地址 301 跳转到此）。
  - 通过 gateway（WebSocket）收事件，不需要公网地址。
  - `MESSAGE_CONTENT`（1 << 15）是特权 intent：要在开发者门户 Bot 页打开，才能放进 `IDENTIFY`；未配置就传会以 close code 4014 断开。
  - 少于 10,000 用户的应用在门户直接开即可，超过要审核；"verification is required for apps in 100+ guilds"。两个数字在同一页出现，门槛具体怎么叠加未确认。
  - 没有该 intent 时，用户内容字段是空的，例外：应用自己发的消息、与应用的私信、提到应用的消息。
- 库：`Rapptz/discord.py` MIT（LICENSE 原文，最近推送 2026-09-07）。

## 题 4：本仓库对话后端

文件：`src/data_agent/web/app.py`（路由）、`web/conversations.py`（261 行）、契约 `tests/acceptance/test_chat_api.py` 开头、`docs/setup.md:105`。

| 要做的事 | 调用 | 返回 / 错误 |
|---|---|---|
| 新建对话 | `POST /api/conversations`，body `{}`（`app.py:155-158`） | 201 `{"id"}` |
| 发消息 | `POST /api/conversations/{id}/messages`，body `{"text", "network"?}`（`app.py:160-169`） | 没有 turn 在跑：201 `{"kind":"turn","turn","run_id"}`；有 turn 在跑：202 `{"kind":"steer","run_id","id"}`（插话，写进子进程 stdin） |
| 读事件 | `GET /api/runs/{run_id}/events?after=<seq>` 返回 JSON；`Accept: text/event-stream` 时是 SSE，`Last-Event-ID` 做游标（`app.py:99-117`） | SSE 每个事件一帧（id 为 `seq`），收到 `result` 后关闭，15 秒一次 keepalive（`app.py:206-235`） |
| 澄清回答 | 没有专门接口：点选项就是一条普通消息（契约第 1 条"a clicked clarification option is such a message"）。澄清事件含 `tool_use_id`、`question`、`options`（2-5 个），写出后该 turn 结束，不写 `answer` 事件，`result` 为成功 | 回答走上面的"发消息"，开新 turn |
| 插话 | 同"发消息"，conversation 正在跑时返回 202 `steer` | 已知限制：`result` 已写、进程未退出的窗口内发的消息返回 202 但送不到（`docs/setup.md:105`） |
| 取消 | `POST /api/conversations/{id}/cancel`（`app.py:171-177`） | 200 行；没在跑返回 409（`conversations.py` 的 `cancel`） |
| 对话状态 | `GET /api/conversations/{id}`（`app.py:148-153`）有 `running`、`turns[].status` | 404 未知 id |

- 一次只跑一条运行，跨表单与所有对话共用，冲突返回 409（契约第 4 条）。空消息 400，单次运行（非对话）不能追问 400。
- 事件类型（取自 `tests/fixtures/web/real/query-shop/events.jsonl` 统计与 `tests/fixtures/chat/fake_chat_run.py:116`）：tool_start、tool_timing、tool_end、sql、thinking、text、answer、status、result、clarification、steer_delivered。适配器渲染所需的事件字段，除上面契约列出的外，未逐个核对。
- 鉴权与监听：`cli.py:35` 的 `WEB_HOST = "127.0.0.1"`，`cli.py:481` 用 uvicorn 启动；`src/data_agent/web/*.py` 里 grep `auth|Authorization|Bearer|cors` 无命中，即没有鉴权。
- 是否适合 IM 适配器复用：接口层面，所有操作都是 JSON HTTP，适配器可作为本机 HTTP 客户端使用，无需改后端。要在同一进程里直接调用 `Conversations` 也可行（`create`、`send`、`cancel` 是同步方法，抛 `Refused(status, detail)`），但 `app.py` 里用 `to_thread` 包装，说明方法是阻塞的。两种方式的取舍属设计决定，这里不选。
- 事实上的限制：对话 id 与 IM 线程 id 的对应关系目前没有存储位置（`conversation.json` 的字段只有 `id`、`created_at`、`turns`，契约第 1 条），适配器需要自己保存映射。

## 题 5：三平台共同点与差异（事实对照，影响"一个抽象 + 三个实现"）

共同点（有证据）：
- 都能不开公网地址收消息（题 3）。
- 都能编辑已发消息，因此"占位消息 + 反复编辑"在三平台都有对应接口（Slack `chat.update`、Telegram `editMessageText`、Discord PATCH）。
- 都有按钮组件，且点击事件都需要在限定时间内确认（Slack 3 秒已确认；Discord、Telegram 的时限未确认）。
- 都有单条文本长度上限，且互不相同。

差异：
- 收消息：Slack 在 Socket Mode 下收到的是带 `envelope_id` 的信封，需逐条 ack；Telegram 是 `getUpdates` 拉取（有 offset、24 小时保留），与 webhook 互斥；Discord 是长连接 gateway，要设 intent。
- 文本上限：Slack 约 4000（40000 截断），Telegram 4096，Discord 2000。
- 内容读取：Discord 需要 Message Content 特权 intent，否则在群频道里读不到未提及机器人的消息内容；Telegram、Slack 无同类开关（Telegram 在群里的隐私模式未查，未确认）。
- 线程概念：Slack 有 `thread_ts` 线程；nao 的 Telegram 线程 id 由 `chat` 库提供，原生 Telegram/Discord 的"线程"与聊天、频道的关系本次未查（未确认）。
- 用户身份：nao 的 Slack 用邮箱匹配，Telegram 用绑定码，两种做法并存；Slack 的 `users:read.email` scope 在 dash manifest 里有，Telegram、Discord 没有邮箱可取（Telegram 无邮箱字段一项为已知常识，未在本次取证中核对）。
- Python 库许可证：slack_bolt MIT、aiogram MIT、discord.py MIT；python-telegram-bot 是 LGPL-3.0（见上，有来源不一致）。
- nao 的现实做法：三个平台各写了一个几乎相同的流程类（telegram.ts 563 行、slack.ts 1928 行），共性靠 `chat` 库与 `utils/messaging-provider.ts` 承担；`chat` 是 JavaScript/TypeScript 库，本仓库后端是 Python，不能直接复用。
